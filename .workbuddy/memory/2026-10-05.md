**三条硬约束**

1. **分组键 / 筛选键用渠道原始首段，绝不用 `ChannelKind`**。`ChannelKind` 只有 5 个成员，
   而它的兜底是「未知 → dingtalk」——Telegram 会话会被**静默**并进「钉钉」组（代码里没有一行
   写着这件事）。展示名走 `channelLabel`，图标才走 `channelIconKind`（图标可以回退，键不行）。
2. **来源判定两个判据不许合并**：`isExternalSession`（`channel` 非空 = 外部来源语义）与
   `channelSessionKey`（id 前缀 = 本地约定）。且「只有前缀、键被截断」返回**空串而非 null**。
3. **筛选态必须放 store**：侧栏 Tab 是条件渲染（`tab === 'tasks' ? … : …`），组件会重挂载，
   组件内 state 会让用户每切一次 Tab 重选一遍。

**IM 会话标题为什么只读**：标题来自网关，本地改名只改镜像，下一轮
`refreshActiveIfChanged` 就盖回去 → 「改了又自己变回去」。快捷入口
（搜索 / 历史提问 / 产物）保留，都是只读动作。

**测试踩到的四点**（两个单测 + 两个真机）：

① 测试里直接 `useXStore.setState()` 不会让订阅组件在本用例内重渲染，必须 `act(() => { … })` 包裹；
② 空态必须自带退路——筛选条在「只剩一个渠道」时会收起，此时点不到 chip，
   退路只能是空态里那个「查看全部」按钮；
③ ⚠️ **Playwright `locator` 绑定「声明时的那个 page」**：真机脚本每场景 `ctx.newPage()`，
   locator 写成模块级常量会让后面的场景一直读旧页面 —— 症状是「正文里已经是『来自 Telegram』，
   断言却拿到『来自 微信』」，看起来像实现了 bug，实际是测试读错页面。每场景重新构造 locator。
④ ⚠️ **点列表行要点行内文字，别点整行**：行右侧「悬停才出现」的快捷入口各自 `stopPropagation`，
   `click()` 默认点几何中心，hover 后中心可能落在快捷入口上 → 点「会话行」实际点了「对话内搜索」。
   给行加 `data-testid="channel-session-row"` + `data-channel` 再过滤。

## FR-5.6 / FR-6.3：投递档位补 `start`（M4 闭合）

用户从三个方案里选了「先做 start 档位」（另两个是：完整 milestone 摘要镜像 / 不做）。

**语义**：三档是**包含**关系 `error` ⊂ `complete` ⊂ `start`。`start` = 在结果之外
**多推一条**「已开始执行」；不做成「只推开始」（那样用户永远拿不到结果）。

**引擎**（`nanobot/nanobot/`）：
- `cron/bound_runner.py`：`_DELIVERY_MODES = ("complete","error","start")` +
  `_DELIVERY_STARTED_TEXT` + `_deliver_started()`，调用点在 `run_bound_cron_job` 写完
  `status="queued"` 之后、`submit_cron_turn` 之前（best-effort，失败只 log）。
- `cron/types.py`：`CronDelivery.on` 注释改为三档 + `milestone` 未实现的**理由**。
- 测试 `tests/cron/test_bound_runner_delivery.py` 15 → 23 例；`tests/cron` 全目录 151 例绿。

**客户端**：`types/task.ts` 抽出 `TaskDeliveryOn`；`ai/runtime/nanobotHttp/tasks.ts` 的 wire
契约同步；`lib/taskDelivery.ts` 文案改成 `Record<TaskDeliveryOn,string>` 映射表
（漏写档位会**编译报错**，嵌套三元只会静默落错分支）；`DeliveryField` 第三个 ToggleButton
（「开始时」必须与「每次执行后」并排读）。

**⭐ 本批最重要的勘查结论（milestone 为什么不做）**：
「节点」信号**早就存在**——`TurnDeliveryFactory._default_route` 对 `channel != "system"` 一律
`publish_lifecycle=True`，而 cron turn 的 channel 是 **origin 渠道**，所以 turn 进行中的
`ProgressEvent`（含 `tool_events`）本来就在经 bus 发出，真发不发由渠道的
`send_progress` / `send_tool_hints` 控制（`ChannelManager._should_send_progress`）。
**但它们发往 origin，不是 `delivery.targets`** → 做 milestone 的真实工作量 =
「把一部分进度镜像到 targets」+「定节流策略」，后者是**打扰预算**（产品决策）。
**不要把结论写成「引擎没有进度事件」**——那是错的，会让下一个人重查一遍。

**两条变异验证**（都确认转红）：① 从 `_DELIVERY_MODES` 去掉 `"start"` → 登记表用例红；
② 去掉 `_deliver_started` 的档位判定（所有档位都推通知）→ `test_non_start_modes_*` 红。

**门禁**：三套 tsc 0 错；全量 vitest **195 文件 / 3004 例**，1 例失败
（`tests/electron/pluginPackage.test.ts` 的 `afterEach fs.rm` hook 超时 = 老环境 flake；
**单文件串行复跑 51 例全绿**，与代码无关）；真机 `tasks/verify-task-delivery.mjs` **三趟全绿**

## FR-2.3 / FR-2.4 勘查结论（决定下一步可行性，2026-10-05）

**FR-2.3 专家** —— 四类绑定的真实状态：

| `imBinding` / `avatar` | ⚠️ 只持久化未消费 |

另两处偏差：① PRD 说内置「招聘/法务/投研/财务/写作」模板，实际 `src/ai/builtinAgents.ts` 只有
通用/文档/数据/牧场 4 条；② **`AgentsPage` 与 `MyAgentsPage` 各有一份专家编辑 Dialog（重复实现），
字段还不一致**——`AgentsPage` 缺工具白名单编辑，同一个专家在两个页面能改的字段不同。

**FR-2.4 专家团三模式** —— ⚠️ **现状下做不了「真实执行」**：

- `mode` 全仓**没有任何执行读取点**（只在类型/标签/表单/卡片/tooltip）→ 仅持久化+展示。
- 团长成员唯一被逻辑读取处是「取首位启用成员当 leader」→ `agentId`，所以**只有那一个成员生效**。
- **引擎只支持匿名子代理**：`SubagentManager` + `spawn` 工具（`agent/subagent.py`、`tools/spawn.py`），
  其 system prompt 固定来自 `agent/subagent_system.md`，**与团成员（具名 Agent）无关联**；
  引擎的 `agent_id`（`api/server.py`）**只用于工具策略，不是人设路由** → 没有「运行某具名 Agent」的概念。
- 另有已知缺陷：`/v1` 链路下 `spawn(wait=false)` 结果**必然丢失**（serve/gateway 两进程各持 MemoryBus）。
- `ProcessView` 的 `ProcessEvent` 无成员字段 → 「谁在跑」无数据源。

→ 结论：**FR-2.4 的「真实执行」需要引擎新增「按具名 Agent 派发」能力**（可复用 `SubagentManager`，
但要把成员的人设/工具/模型传下去），属大工程 + 需产品定义编排语义（谁汇总、失败怎么办、上下文怎么传）。
**在此之前，UI 必须如实说明「模式当前只保存不生效」**——这与 milestone 那次是同一类坑
（让用户以为选了就会生效）。

### 用户报的真机缺陷：模型选择框 label 与值文字重叠（已修）

用户截图：`模型（可选）` 与框内值文本（`qwen3.8-flash`）叠在同一位置。

**根因**：MUI 按「值是否为空」决定 `InputLabel` 下沉还是浮起，而本控件用 `displayEmpty` 在
**空值时也渲染了一行文案**（`Auto · xxx`）→ 下沉的 label 与它压在同一位置。
⚠️ 我先前只处理了 `displayEmpty`（解决「留空时框内空白」），**没意识到它是成对的两个坑**。

**修法**：`InputLabelProps={{ shrink: true }}`（label 常浮起，因为本控件框内始终有文案）。

**验证（量几何，不看 class）**：
```
不 shrink → label.bottom=605.4 > 值文本内容区顶=582.9（重叠）
shrink    → label.bottom=574.7 ≤ 582.9（不重叠）
```
变异（去掉 `shrink`）确认真机断言转红 ✓。断言已并入
`tasks/verify-agent-model-binding.mjs`（长期回归保护），截图 `tasks/agent-model-1-default.png`。

⚠️ **判据本身也踩过一次**：最初拿 `label.bottom` 与 `.MuiSelect-select` 的 **border-box 顶边**比，
得到「永远重叠」的假阳性——浮起的 label 半压在边框线上，必然与 border-box 相交。
正确做法是比**值文本的内容区顶边**（border-box 顶 + `padding-top`）。已写进 skill §7.35.4。
