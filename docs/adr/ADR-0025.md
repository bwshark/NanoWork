# ADR-0025：应用级扩展运行时——fork 独立进程 + 显式权限面 + 与插件分工（抄进程隔离，不抄 Module Federation；不做 Guest 桥接 SDK）

| **状态** | 新建 |
| **实现核对** | ⬜ 未实现（本 ADR 通过即视为 V1.6 B8 完成，实施另排） |
| **决策日期** | 2026-10-17 |
| **相关章节** | v2 第 12.5–12.8 节（四级扩展生态 / WorkBuddy 分发源实测）；V1.6 计划书 FR-3.14 |
| **v2 原文表述** | PRD「四级扩展生态」只列了名字、**零实现**；WorkBuddy 的 `extensions/` 是 8 个 **fork 独立 Node 进程** + `distribution.json`，入口经 `main/preload/fork-preload.cjs` → `runExtension({extensionId, env, activate})` |

## 决策

**扩展 = 应用级功能单元，跑在 fork 出来的独立 Node 进程里；插件 = agent 能力单元，跑在引擎进程内。两套机制不混。**

- **进程模型**：扩展经 `child_process.fork()` 起独立进程，入口是 `runExtension({extensionId, env, activate})`。**不抄 Module Federation**（见「备选方案」）。
- **权限面**：扩展**默认没有任何能力**，能拿到的东西由 manifest 显式声明（IPC 通道白名单 + 文件根 + 出网域名），由主进程在 `fork` 时按声明装配。未声明 = 拿不到，而不是「先给全量再回收」。
- **生命周期**：`activate` / `deactivate` / `崩溃重启` 三态，主进程持有唯一权威；扩展进程崩了只杀自己，主进程记录 `lastError` 并可选择重启（**不自动重启超过 N 次**）。
- **与插件的分工**：插件给 **agent** 加能力（技能 / 提示词片段 / 工具 / MCP），消费方是**模型**；扩展给**应用**加功能（新面板 / 新侧栏动作 / 新导出格式），消费方是**用户**。两者加载器、分发源、版本缓存、权限面**全部独立**。

## 背景

1. **为什么需要扩展这一层**：插件的能力面被「模型的工具」这个形状限死了——它能给模型加工具，但不能给应用加一个「把会话导出成 PDF」的按钮，也不能加一个常驻侧栏。这类需求的消费方是人，不是模型。
2. **为什么不能复用插件机制**：插件运行在引擎进程内，与模型共用同一个解释器与工作区作用域。把「应用功能」塞进去，等于让第三方代码与智能体共享同一份凭据作用域——而 `no_access` 那套硬边界的前提正是「进程内只有引擎自己」。
3. **为什么不能直接写进主进程**：`main.ts` 已经是 4700+ 行的单文件，再往里加功能模块会把「窗口 / 托盘 / 网关 / 插件 / 同步 / 诊断」耦成一坨；且任何第三方功能进了主进程就拿到了 `safeStorage`、`fs`、`shell`。

## 备选方案

### ① Module Federation（UI 联邦）——**不采用**

把扩展编译成 remote entry，由宿主在运行时拉取并挂载。

- **否决理由一（构建耦合）**：MF 要求共享依赖的**单例**（React / MUI / emotion）。一旦某个扩展用了不同大版本的 React，症状是 hooks 崩在「Invalid hook call」——而这个错误信息与真因相隔三个模块，排查成本极高。本项目的渲染层是「一个 Vite 产物 + Electron `loadFile`」，加 MF 等于给首屏再加一层运行时协商。
- **否决理由二（权限面无处安放）**：MF 的远程代码**跑在渲染进程里**，与主进程同权。我们要的「默认没有任何能力」在 MF 下只能靠自觉——而扩展恰恰是第三方代码。
- **否决理由三（首屏）**：FR-13.5 刚把首屏从 2.19 MB 压到 1.15 MB，MF 的共享作用域会把「扩展的依赖」重新变成首屏的一部分。

### ② 渲染进程内 iframe / WebWorker —— **不采用**

- iframe 拿不到 Node 能力（扩展恰恰常需要 `fs` / `child_process`）；给它 `nodeIntegration` 就回到了「第三方代码与主进程同权」。
- WebWorker 没有 DOM，做不了面板类功能。

### ③ Guest 桥接 SDK（给第三方 UI 扩展用的薄 SDK）——**本期不做**

WorkBuddy 的做法是提供一份 SDK，第三方 UI 扩展通过它与宿主对话。

- **不做理由一（没有需求方）**：当前没有任何「第三方 UI 扩展」的实际诉求；为一个不存在的生态先定 SDK 形状，等于把接口冻结在最猜的那个版本上。
- **不做理由二（它会逼出第二套权限模型）**：SDK 一旦存在，权限就从「manifest 声明的 IPC 白名单」滑向「SDK 暴露了多少方法」——后者是**代码即权限**，而前者是可审计的数据。本项目在 FR-2.2 / FR-8.13 上已经两次把「代码即权限」换成「声明即权限」。
- **何时重新评估**：出现第一个真实的第三方 UI 扩展需求时，并且那时的 manifest 权限面已经稳定运行过一个版本。

## 后果

- **正面**：扩展崩溃的影响面被限制在它自己的进程里（主进程与引擎都不受影响）；权限是一份可审计的数据而不是代码表面积；`main.ts` 不再继续膨胀。
- **代价**：
  - 扩展与宿主之间只有 IPC，**没有共享内存 / 共享 store**——扩展想读会话列表必须走 IPC，延迟比进程内调用高一个量级。这是「隔离」的对价，不是缺陷。
  - 分发与版本缓存要另做一套（插件的 `marketplace.json` + `cache/<market>/<name>/<version>/` 那套**不直接复用**：插件副本要被引擎 import，扩展副本要被 fork，两者的落点与指纹都不同）。
  - `distribution.json` 的格式需要重新设计（WorkBuddy 那份是按「8 个内置扩展 + 整包发版」做的，与本项目「版本化缓存 + `current` 指针」不一致）。
- **与既有决策的关系**：ADR-021（工具权限唯一收口在引擎）不受影响——扩展**不**给模型加工具，那是插件的职责；若未来扩展需要调工具，必须经引擎的 `/v1`，由引擎侧的 `agent_blocks_tool` / 审批门裁决，**不允许扩展直连工具系统**。
- **落点（实施时）**：主进程新增 `electron/extensionHost.ts`（fork / 权限装配 / 生命周期）+ `electron/extensions/<id>/`（每个扩展一个入口目录）；manifest 形状进 `src/types/extension.ts`；渲染层经既有 `platform` 适配层访问，**不新增 `window.electronAPI` 直连接口**（CI 检查一）。

---

> 本 ADR 只定方向，不承诺实现排期。实施前需先补两件事：① 扩展 manifest 的 schema（含权限声明）；② 与插件市场**共用还是分用**一个分发源的结论（当前倾向分用，理由见「代价」第二条）。
