## 决策

**用户数据目录分四个根：**

- **① `~/.nanowork`** —— 产品自有用户资产（settings / mcp / channels / experts / skills 索引 / 记忆 / prompts / audit）。
- **② `<userData>`** —— Electron 的实现细节（卸载即可能被清）。
- **③ 引擎配置目录** / **④ 引擎工作区** —— 引擎按 config 自己寻址，**不得**「统一」到 ①，否则引擎会找不到文件（`FR-5.x` 的 cron 热加载随之失效）。

③④ 的路径只允许一个来源：`resolveNanobotWorkspacePath()`。

## 背景

用户数据散落在各处的后果很具体：卸载可能清掉用户资产、
同步时找不到「哪些文件属于谁」、引擎自己寻址的目录被客户端「统一」后引擎找不到文件。

## 后果

- **正面**：用户资产只进 ①（可同步、可迁移、卸载不丢）；引擎产物留在 ③④（引擎自洽）。
- **代价**：渲染层持久化须从 ② 的单文件迁向 ①（→ ADR-019）。
- **实现核对（2026-09-17）**：①~④ 的划分已落（`src/platform/storage.electron.ts` + `electron/storageRoutes.ts`），`sessions` / `tasks` / `artifacts` 作为**过渡落点**仍留 ②，待 D2 实体化结构（`projects/<slug>/*.jsonl` + `index/sessions.db`）落地后消化。见 v2 第 18.2 节的逐项对照表与第 18.2.5 节。
