## 决策

**工具权限的唯一收口落在引擎：**

- 收口点是 `before_execute_tool` 的**否决通道**（hook 拒绝即不执行）+ 审批回传端点 `POST /v1/tool-approvals/{id}`（SSE 只出不进，裁决必须单独回传）。
- `access_mode`（作用域）与 `tool_approval`（询问）是**正交两轴**；`full` 作为更粗开关覆盖逐条批准。
- 三个 fail-closed 不变量；非流式（multipart）路径无审批通道，必须 fail-closed。

取代 v2 第 11.1 节的客户端 `ToolGateway` 草案（保留为 V3 多引擎参考形态）。

## 背景

客户端只收到单向 SSE，看不见也拦不住引擎进程内的工具执行——
把门控写在客户端是「给没有门的墙装锁」。这是 ADR-001（独立进程）的直接推论。

## 后果

- **正面**：门控落在真正执行工具的地方，提示词绕过无效；`full` 也不跳物理兜底。
- **代价**：引擎侧需维护 vendored fork 的 `[LOCAL PATCH]`（见 `docs/upstream-merge-conflicts.md`）；非流式路径须 fail-closed（能力换安全）。
- **落点**：引擎 `nanobot/agent/hook.py:69`（否决通道）、`nanobot/agent/hooks/tool_approval.py`、`nanobot/security/tool_approval.py`（`decide_tier`）、`nanobot/api/server.py:768`（回传端点）；客户端 `components/PermissionDialog.tsx`、`src/types/permission.ts`。
