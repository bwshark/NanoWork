# 增量 PRD：工作区文件记忆（MEMORY.md 机制）

> 本文件为 `docs/prd.md` 的增量补充，仅描述 P1「工作区文件记忆」变更部分，不重写既有 P0 需求。
>
> **2026-09-17 实现对齐与修复**：§3 与 §5 中若干条与实现不一致（落点写成「工作区根目录」、
> 自动摘要「默认关」）。§6 记录两处**刻意偏离**（6.1 落点 / 6.2 默认开）及理由，以及
> 当日的四次修复——**6.4 两层合并注入（P0）**、**6.5 系统报错不落盘（P1）**、
> **6.6 语义重复不落盘**、**6.7 注入快照失效机制**。§6.3 与 §6.8 是既有的协议与边界说明。
> 排查过程与磁盘证据见 `.workbuddy/reports/memory-diagnosis-2026-09-17.md`。

## 1. 需求目标与价值
让客户端沉淀一份可读、可编辑的长期记忆文件，把多轮及跨会话的任务上下文、用户偏好、关键结论持久化为 Markdown。新会话可将其作为上下文注入 Agent，实现"越用越懂你"的长期记忆，弥补当前会话隔离导致的信息丢失，且复用已有 `platform.writeTextFile`/`platform.storage` 能力，跨端零侵入。

**落点（与初版描述的差异）**：不写在「工作区根目录」，而是收在用户的资产目录下，分两层
（详见 §6.1）——①用户级 `~/.nanowork/MEMORY.md`；②工作区级
`~/.nanowork/memory/<workspaceKey>.md`。用户的工作目录不被产品写入任何文件。

## 2. 用户故事
- **查看记忆**：As a 用户, I want 在"记忆"入口查看长期记忆原文与**它在磁盘上的位置**, so that 我能知道 Agent 记住了什么、存在哪。
- **Agent 自动沉淀记忆**：As a 用户, I want 会话结束后自动把关键结论摘要写入记忆, so that 下次会话无需重复交代背景。
- **记住我是谁**：As a 用户, I want 我告诉过 Agent 的称呼/职业在新会话里依然有效, so that 跨项目都不用重复自我介绍。
- **手动编辑记忆**：As a 用户, I want 在聊天页把某条回复"保存为记忆"并手动编辑记忆页, so that 我能主动控制长期记忆的准确性。

## 3. 需求池
- **P0** 记忆存储：分两层落 Markdown。用户级 → `~/.nanowork/MEMORY.md`；工作区级 →
  `~/.nanowork/memory/<workspaceKey>.md`（key = 工作目录的 `<basename>-<hash8>`，
  见 §6.1）。Electron 由主进程 `storageRoutes` 把 storage key 路由成真实文件；
  Web 经 `platform.storage` 落 localStorage（另有导出下载）。
- **P0** 记忆读取：新会话创建时自动读取 MEMORY.md；以可开关的"记忆上下文"注入 system prompt 末尾（开关存 `settingsStore`）。
- **P0** 手动写入：聊天页消息操作菜单提供"保存为记忆"（追加带时间戳的引用块）；"记忆"页支持在线编辑并保存。
- **P1** 自动沉淀：会话结束触发摘要。触发点为**两个**——关闭/删除会话、**新建会话**（切走时对上一个会话补触发）；策略 = 调用模型生成 ≤150 字**分节**摘要，分节落盘、幂等去重（详见 §6.2）。
- **P1** UI 落点：设置页新增"记忆"分区 + 独立"记忆"入口页；聊天页消息 hover 菜单含"保存为记忆"。
- **P2** 多工作区记忆隔离与导入/导出。
- **P2** Agent 受控写入：Agent 可在回答里用 `<memory-save scope="…">` 声明「这条请记住」，由客户端完成落盘（见 §6.3）。

### 与现有 store 关系
- `agentsStore.agent.systemPrompt`：记忆**不**写入 systemPrompt 字段，仅运行时注入，保持 agent 模板纯净。
- `sessionsStore`：在 `createSession` 阶段读取记忆并拼装上下文，不持久化记忆内容本身。

## 4. UI / 交互设计要点
```
设置页 ── 记忆 [开关: 注入记忆上下文] [开关: 会话结束自动沉淀摘要] [打开记忆页]
聊天页 ── 消息 hover → "💾 保存为记忆"
记忆页 ── ┌────────────────────────────────────┐
          │ [用户级 | 工作区级]  落点: ~/.nanowork/memory/<key>.md │
          │ (可编辑正文)                        │
          │ [保存] [导出] [清空]                │
          └────────────────────────────────────┘
```
新建会话时若记忆非空，聊天顶部显示"已加载 N 条记忆"提示条，可临时关闭。

## 5. 待确认问题（已定论）
1. 自动摘要默认开还是关？**已定论：默认开**（`settingsStore.DEFAULT_SETTINGS.autoSummarize = true`，persist v9 迁移把历史 `false` 提升为 `true`）。理由见 §6.2。
2. Web 端记忆存 localStorage 还是强制下载文件？**已定论：localStorage 为主，提供导出。**
3. 记忆注入位置（system prompt 末尾 vs 独立 context 块）？**已定论：system 段末尾，标签包裹**，且 identity 段必须排在 memory 之前（护栏句指向「上方」）。
4. 自动摘要调用哪个模型？**已定论：随当前连接直连 nanobot 网关；网关离线时静默跳过。**
5. 多工作区如何判定根目录？**已定论：以会话的 workdir 为 key（归一化 + 哈希），见 §6.1。**

## 6. 实现对齐（2026-09-17）

**本节导航**：6.1 落点与 key（刻意偏离）｜6.2 自动沉淀（刻意偏离：默认开）｜6.3 Agent 写入协议｜**6.4 两层合并注入**｜**6.5 系统报错不落盘**｜**6.6 语义重复不落盘**｜**6.7 注入快照失效机制**｜6.8 与引擎记忆的边界。加粗四节为 2026-09-17 的修复，均附症状 / 根因 / 修复 / 回归防线。

### 6.1 两层落点与工作区 key

| 作用域 | 落点 | workspace key | 写入方 |
|---|---|---|---|
| 用户级（L2） | `~/.nanowork/MEMORY.md` | 不适用 | 记忆页手动编辑；自动沉淀的**身份类**分节；Agent `<memory-save scope="user">` |
| 工作区级（L3） | `~/.nanowork/memory/<key>.md` | `workspaceKeyFor(workdir)` | 自动沉淀的**任务类**分节；「保存为记忆」；Agent 默认档 |

`workspaceKeyFor` 形态 `<basename>-<hash8>`（如 `nanowork-1a2b3c4d`）：
带 basename 是为了让文件名可读（纯哈希会让「去哪个文件找记忆」变成猜谜）；
只做三件归一化（反斜杠→斜杠、去尾斜杠、转小写），因为 Windows 路径大小写不敏感，
`D:\Work` 与 `d:/work/` 必须落同一个 key，否则同一工作区的记忆被劈成两半。
无 workdir（IM 会话 / 历史数据）回落 `default`，与升级前的数据保持连续。

> **初版为何写成「工作区根目录」**：那是 follow 了 WorkBuddy 的形态
> （`<workspace>/.workbuddy/memory/`）。实际实现选择收在用户资产目录，
> 理由是①不往用户的项目目录里塞产品文件；②同一个工作目录可以被多个 Agent 使用，
> 记忆属于用户而非项目。**这是刻意偏离，不是未实现。**

### 6.2 自动沉淀：两个触发点 + 分节分流

触发点（对齐「会话结束（关闭 / 新建会话）」）：
- `deleteSession` / `deleteSessions`；
- `createSession` —— 对**上一个会话**补触发。这一处曾完全缺失，导致
  「说一句 → 直接新建会话 → 问我是谁」整段落在空档里。

守卫（`sedimentSession` 内部，单条与批量同一条规则）：
`autoSummarize` 关 → 跳过；`readonly` 或 `cron:` 前缀 → 跳过（自动任务分组动辄
几十条 run，逐条调模型既慢又无检索价值，且这些 run 的真值在引擎侧）；无消息 → 跳过；
同一会话只沉淀一次（模块级去重集）。

**为何默认开而不是默认关**：初版推荐「默认关，首次手动开启并提示」。实测后果不是
「少写一点记忆」，而是整条链路从未被触发——用户告诉 Agent 自己的名字，新会话依然
一问三不知。自动沉淀是记忆的**唯一自动写入源**，默认关等于默认没有记忆。

**为何分节**：「落到哪一层」由内容性质决定，不能由调用方一刀切：
称呼/年龄段/职业/稳定偏好是**跨项目**事实（换个工作区依然成立 → L2）；
本次会话的决策/待办/项目专有事实只对当前工作区有意义（→ L3）。
初版提示词只保留「决策/偏好/待办」三类，身份类事实不在三类里，**整段被丢弃**——
这正是「我告诉过它我叫什么，新会话却不知道」的直接原因。

### 6.3 Agent 侧受控写入协议

Agent 在回答末尾写 `<memory-save scope="user|workspace">…</memory-save>` 声明意图，
由客户端解析 → **剥离标记**（不进入用户可见正文，也不进入事件流）→ 交
`MemoryService.append` 落盘（时间戳/来源/幂等标记由它统一负责）。

不走工具调用的理由：「记一条偏好」是纯本地无副作用写入，弹审批框只会教会用户
把审批全关掉。协议与记忆能力同开同关（`memoryEnabled && autoSummarize`）。

### 6.4 两层合并注入（P0 修复，2026-09-17）

**症状**：在 `D:\test` 说「我叫明明」，`D:\test` 里问得出来，换到 `D:\tmp` 就问不出来。

**根因**：写入分了层，读取没跟上。

| 侧 | 行为（修复前） |
|---|---|
| 写 | `identity → L2`（`~/.nanowork/MEMORY.md`）、`task → L3`（`memory/<key>.md`） |
| 读 | `loadMemoryInto` 只 `load('workspace', key)` —— **全仓生产链路上 `load('user')` 零调用** |

于是 L2 是一份**写得进、读不出**的文件。`D:\tmp` 之所以会答「USER.md 里没有姓名」，
是因为注入块为空后模型退回去翻了身份文件模板——那是**兜底行为，不是记忆生效**。

**修复**：新增 `MemoryService.loadForInjection(workspaceKey)`，并行读两层 →
`composeMemoryForInjection` 合成为一段正文 → 由 `wrapForInjection` 包成注入块。
要点：

1. **定序固定「用户级在前、工作区级在后」**，并在护栏句补一句裁决规则
   （「两者冲突时以用户级为准」）。顺序与护栏句是同一套假设，不可只改一边。
2. **`entries` 取两段各自计数之和**，而不是对合成文本调 `countEntries`——
   合成文本多了段标题，计数会漂。
3. **段标题用 `【…】` 而非 `## `**：记忆正文可能是用户手写的 Markdown，
   `countEntries` 优先按 `## ` 计数，加两层二级标题会让「已加载 N 条记忆」多出两条。
4. **只有一层有内容时照样带标题**：让模型看得出这条记忆的适用边界；
   两层皆空仍走「空记忆」分支（`session.memory = ''`，避免每轮发送都重读盘）。

回归防线：`tests/memoryScope.test.ts`（合成定序 / 只写用户级也能读到 / 条数）、
`tests/sessionsPromptAssembly.test.ts`（**两层真的都进了请求的 system 段**——
「函数对了但没接线」是本仓库踩过的坑）。

### 6.5 系统报错不落盘（P1 修复，2026-09-17）

**症状**：`~/.nanowork/memory/<key>.md` 里躺着这样一条「记忆」——

```
> [2026-09-17T04:38:15Z] 来自「auto:你好，我叫什么？」
> The AI provider rejected the request because the API key is out of quota…
```

**根因**：网关在配额 / 鉴权失败时，会把**错误文案当作正常 `delta.content`
吐进 SSE 流**。通道层面分不出这一帧是回答还是报错，于是：

| 环节 | 实际发生了什么 |
|---|---|
| `summarize` | `onToken` 把错误原文当模型输出收下（`onError` 当时是空实现，不拦） |
| `parseSummary` | 错误原文不含 `[身份]/[任务]` 标签 → 走**整段降级**分支 → 当作 `task` |
| `append` | 以「会话摘要」的名义写进工作区级记忆 |

一条系统报错就此成为长期事实，此后每次会话都被注入。触发它的那轮对话本身也是
失败的（provider 报错），归纳它没有任何信息价值。

**修复**：三道防线，都收敛到「两节皆空 / 该条不计入」，调用方无需区分
「没内容」与「被拦下」。

1. **入口剔除**（`summarize`）：历史条目里像系统报错的消息不进入归纳输入。
   剔除而非整段放弃——一段几十轮的对话可能只有最后一轮撞上报错。
2. **入口守卫**（`summarize`）：过滤后**一次有效回答都没有**的会话直接跳过。
   这一条正好覆盖「用户提问 → provider 报错 → 助手无正文」的完整事故形态，
   且守卫在调模型之前，不浪费一次归纳请求。
3. **出口判定**（`parseSummary`）：整段像系统报错 → 返回两节皆空。
   放在标签切分**之前**：报错文案偶尔粘连半截标签，那种「半截身份」同样是垃圾。

**`looksLikeSystemError` 的判据取舍**（`src/lib/memory.ts`）：要求
「命中强特征词（`out of quota` / `api key` / `rate limit` / `ECONNREFUSED` …）
**且** 中文字符占比 < 15%」双重成立。

- 只看特征词会误杀「用户正在排查 API key 配额问题」这类正常摘要——中文摘要里
  出现英文术语是常态，所以必须叠加语言判据。
- **已知代价**：中文错误文案认不出来（中文报错与中文摘要在语言上无法区分），
  这类漏判由 `onError` 通道兜底——`summarize` 里上报过错误的流，已累积的
  `text` 一律丢弃（可能前半截正常、后半截报错，「半正常」比纯报错更危险）。

**输入侧同步收紧**（`sessionsStore.sedimentSession`）：被用户中断（`aborted`）的
助手消息是半截回答，不作为归纳依据——与正文里 `<memory-save>` 指令块按 `aborted`
跳过同源。用户提问本身保留：话已经说出口，被中断不代表没说过。

回归防线：`tests/memoryService.test.ts`（报错原文 / 带标签报错 / 中文摘要不误杀 /
`onError` 丢弃 / 无有效回答不调模型）、`tests/sessionsStore.test.ts`（中断消息
不进归纳输入，用户提问保留）。

### 6.6 语义重复不落盘（2026-09-17）

**现象**：用户级 `MEMORY.md` 里同时躺着三条几乎同一件事的记忆——都是「明明 / 20 岁 /
新疆 / 返京」，措辞不同，来自三个不同的写入方：

| 时间 | 来源标记 | 实际写入方 |
|---|---|---|
| 16:55:55 | `auto:…` | 自动沉淀的 `[身份]` 节 |
| 16:56:09 | `agent` | 模型主动写的 `<memory-save scope="user">` |
| 17:14:16 | `agent` | 同一条事实，17 分钟后又被写了一遍 |

**根因**：去重是**字节级**的。`append` 只算 `hash(正文)` 并比对已有标记，因此只能挡
「一字不差」的重复；同一事实换一种措辞（改标点、换语序、省略连接词）哈希必然不同，
三条全部落盘。在此之上还有两层放大：两个写入源互不知情且都会重复触发；且新会话会把
已有记忆整段喂回模型，模型看到「已记过明明」仍会再写一条——它不知道去重是字节级的。

**为什么不提高比对精度来解决**。曾打算用 bigram Dice / 覆盖率做模糊判定，拿这三条真实
数据实测后发现这条路在中文短文本上不成立：

| 对照 | 覆盖率 | Dice |
|---|---|---|
| 真实的两条改写式重复（**该判重**） | 0.25~0.45 | 0.22~0.35 |
| 「20 岁」→「25 岁」（**这是更新，不该判重**） | 0.90 | 0.90 |
| 「偏好简洁沟通」是「…，关注 AI 动态」的前缀（**该补充，不该判重**） | 1.00 | 0.56 |

要抓住改写式重复，阈值必须压到 0.45 以下，而那会把「年龄更新」和「同前缀补充新信息」
一并误杀——**静默丢记忆比多存一条严重得多**。「重复 / 更新 / 补充」三者在字面上不可
区分，因为区分它们需要知道**哪部分是事实的键**，这是语义问题不是字符串问题。

**方案：把语义判断交回给有能力做它的那一层。**

1. **语句级去重（机械重复兜底）**——归一化后完全相等即跳过：
   - `normalizeForDedup(text)`：去全部空白、去标点与 Markdown 装饰符、统一小写。只做
     无信息损失的三件事，不做同义词替换或语序调整。
   - `parseEntryBodies(text)`：从记忆全文里取出各条**正文**（引用块格式跳过
     `[时间] 来自「…」` 与 `<!-- SUMMARY:… -->` 两行；用户手写的 `## ` Markdown 也支持）。
   - `append` 命中即返回 `skipped-duplicate`，不落盘。
2. **语义去重（主力）**——让模型看到已有记忆后再决定写不写：
   - `<memory-save>` 路径：`MEMORY_WRITE_INSTRUCTION` 要求模型**写之前先核对上文已注入
     的记忆块**；明确「若是对已有事实的更新，只写新的完整表述，不要留下多个版本」；
     并禁止「已为用户完成 X」这类一次性操作播报。
   - 自动沉淀路径：`summarize(history, { knownFacts })`，`knownFacts` 取
     `loadForInjection(workspaceKey)` 的结果。规则措辞刻意并列「新增」与「变化」——
     只说「不要重复」会让模型把更新也当成重复丢掉。

**`append` 的返回值**从 `void` 改为 `'written' | 'skipped-empty' | 'skipped-duplicate'`：
调用方可以继续 `await` 后忽略（TS 合法），但测试与记忆页需要区分「写进去了」与
「因为重复被跳过」。

回归防线：`tests/memoryService.test.ts`——归一化抹平标点、**三条真实重复归一化后仍互不
相同**（这条用例把「为什么不做模糊阈值」钉成了可执行的文档）、条目正文解析（引用块 +
手写 Markdown）、同句换标点不重复写入、**年龄更新照常写入**、**同前缀补充信息不被吞**、
空内容返回 `skipped-empty`、`knownFacts` 进了 system 段且规则含「变化」二字。

**已知残余**：模型对提示词的遵守是软约束。若它仍然写出措辞差异极大的重复，代码层不会
拦截（拦它就会误杀更新）。剩余的概率性重复由「记忆页人工合并」兜底——那是 P2，
尚未实现。

### 6.7 注入快照的失效机制（2026-09-17 修复）

**症状**：记忆文件里明明写着「用户擅长前端 GIS 开发」，紧接着提问却答不出来。

**根因不在模型，也不在写入，而在快照永不失效**：`session.memory` 只在
`createSession` / `loadSession` 生成一次并缓存，`send` 路径原本明确「不补读」
（补读会插入 async 边界）。于是会话一旦建立，此后所有写入——本会话上一轮的
`<memory-save>`、别处会话结束时的自动沉淀、记忆页的手动编辑——都进不了这一轮注入。

**证据**：事件流里存着**完整请求体**。写入落盘后 13 秒与 57 秒的两次提问，注入的
MEMORY 块与写入前逐字节相同。这排除了「模型没看见」以外的所有解释。

**修复**：给快照补上两个「产出依据」，并新增同步的过期判定。

| 项 | 内容 |
|---|---|
| `Session.memoryVersion` | 生成快照时的 `MemoryService.writeVersion()` |
| `Session.memoryWorkspaceKey` | 生成快照时的 `workspaceKeyFor(workdir)`（改了目录，同一份快照就指向另一个文件） |
| `isMemorySnapshotStale(id)` | **同步**判定：版本不等、或 workspaceKey 不等即过期；`memoryVersion === undefined`（预热在途）一律返回 false，避免误刷 |
| `MemoryService.writeVersion()` | 单调递增，**唯一递增点是 `save()`**（`clear`/`append` 都经它），递增放在写入**完成之后** |
| 补刷点 | `selectSession`（切回会话）+ `streamAssistantReply` 步骤 0.1（发送前） |

**顺序是硬约束**：补刷要读盘（异步），而「已水合的会话 `send` 同步进入流式态」是
仓库既有的可测性质——同一会话并发 `send` 互斥、不同会话可并发，全靠流式槽位在同步段
内落位。因此 `streamAssistantReply` 里**先同步占住槽位、再 await 刷新**，两个目标
才能同时成立。把刷新挪回 `send`（即挪到槽位之前），那条性质立即失效。

回归防线（`tests/sessionsStore.test.ts` + `tests/sessionsPromptAssembly.test.ts`）：
- 端到端：本轮写下的 `<memory-save>`，**下一轮发送立即生效**（不重开会话）；
- 切回已加载的会话时，期间有写入则刷新快照；
- workdir 变化也算过期；
- **快照过期需要刷新时，`send` 仍同步进入流式态**——这条用例是把刷新挪回
  `send` 就会立刻失败的守门人（`expected undefined to be defined`）。

### 6.8 与引擎侧记忆的边界（易混）

本项目有**两套互不相干**的记忆，别当成同一件事：

| | 客户端记忆 | 引擎（nanobot）记忆 |
|---|---|---|
| 落点 | `~/.nanowork/MEMORY.md`、`~/.nanowork/memory/<key>.md` | `agents.defaults.workspace/memory/MEMORY.md` |
| 写入方 | 本 PRD 描述的全部路径 | 引擎的 Dream 归纳（定时批处理） |
| 是否随会话 workdir 变化 | **是**（L3 按 key 隔离） | **否**（绑定引擎配好的那个 workspace） |

引擎记忆的 workspace 由 `nanobot.config.json` 决定（本项目为
`<repo>/.nanowork-Workspace`），`build_system_prompt(workspace=…)` 只影响
prompts/skills 覆盖，**不改记忆落点**。因此不要期望「换个工作区，引擎记忆跟着换」。
