# FR-2.6 组织资产：服务端 + 客户端落地记录

> **状态**：服务端 + 客户端已落（2026-11-03）。
> **需求出处**：`docs/nanowork-prd-design-v2.md` 第 3 章 `FR-2.6`（P2，M7，"管理员把个人 Skill / 专家 / 提示词模板发布为组织资产，全员可见"）。
> **本文用途**：记清楚「为什么发布的是快照而不是引用」「为什么载荷里必须剥掉两个字段」「为什么导入不重复记账」，避免下一轮把同一处再想一遍。

---

## 一、先定边界：为什么不是「共享本机资产」

专家（`agentsStore` 的 localStorage）、技能（`~/.nanowork/skills/*/SKILL.md` 扫描结果）、
提示词模板（`~/.nanowork/prompts/**` 覆盖正文）全都是**本机资产**，云端拿不到、也不该拿
（同步层只传用户意图，见 `src/types/skill.ts` 关于「扫描结果不上云」）。

所以 FR-2.6 的实现是**内容快照 + 全员下发**，不是「把本机那条记录共享出去」。推论有两条，
都必须写进代码：

1. **快照是死的**。发布者改了本机那个专家，组织里那份**不会变**，要重新发布。反过来也成立：
   别人导入后改了，组织里那份不受影响。这不是缺陷 —— US-10「人走了经验还在」要的正是
   一份不再依赖任何人的副本。
2. **载荷里不能有机器 / 账号专属字段**。`path` 是**别人机器上的路径**，`imBinding` 是
   **别人账号的机器人绑定**（FR-10.5 禁止上云）。`knowledge` 也是组织专属（存的是发布者
   所在组织的库 id，换组织就指不到东西）。三者带上任何一个，导入方都会得到一个
   「看起来配好了、实际指不到」的坏配置。

## 二、服务端（`cloud/app/orgassets/`）

### 2.1 一张表

| 表 | 主键 | 字段 |
|---|---|---|
| `org_assets` | `id` | `org_id` / `kind`（`agent`·`skill`·`prompt`）/ `name` / `description` / `payload`（JSON **文本**）/ `published_by` / `published_at` / `updated_at` |

`payload` 存 TEXT 而不是方言 JSONB：开发 SQLite、生产 PostgreSQL，两边都要能存
（与 `db.py` 的「同一份 schema 两个库」同一条约定）。表由 `create_all` 新建，
**不需要**动 `migrations.py::ADDED_COLUMNS`。

### 2.2 端点（4 个）

| 方法 | 路径 | 权限 |
|---|---|---|
| GET | `/api/orgs/{org_id}/assets?kind=` | **组织成员**（非成员 404） |
| POST | `/api/orgs/{org_id}/assets` | 组织 `admin` / `owner`（成员 403） |
| PATCH | `/api/orgs/{org_id}/assets/{asset_id}` | 组织 `admin` / `owner` |
| DELETE | `/api/orgs/{org_id}/assets/{asset_id}` | 组织 `admin` / `owner` |

两处 404 语义不同，都要保留：

- **不是本组织成员** → 连列表都 404（组织 id 可枚举，403 等于确认组织存在）；
- **资产不属于这个 org** → 拿 A 组织的资产 id 去 B 组织路径下操作一律 404。少了这条，
  多组织管理员就多了一条跨组织改别人资产的通路。

### 2.3 载荷护栏（服务端的唯一职责就是这几条）

| 护栏 | 行为 |
|---|---|
| `kind` 闭集 | 不在 `agent`/`skill`/`prompt` 里 → **422**（pydantic 的 `Literal`） |
| 必需字段 | 缺 `systemPrompt`（agent）/ `prompt`（skill）/ `kind·key·text`（prompt）→ **400**，文案点名缺哪个 |
| 提示词槽位种类 | 只能是 `mode` / `domain` / `style` → 否则 400 |
| 机器专属键 | 载荷里（**递归**）出现 `path` / `imBinding` → **400**，文案点名是哪个键 |
| 体积 | 序列化后 > 64 KiB → 400 |

为什么必需字段要在服务端校验：`payload` 是自由 JSON，一个拼错字段名的客户端会发布出
一堆「点开是空白」的资产，而这种坏数据在列表里看起来完全正常。

为什么 `path` / `imBinding` 要**拒绝**而不是静默剥掉：客户端已经剥了一次（为了让发布成功），
服务端这一次是为了让**漏剥的客户端报错**。悄悄剥掉等于放过一个还在泄露本机路径的版本。

### 2.4 刻意不做：同源去重

POST 永远新建，不按 `name` 或原始 id 合并。合并的失败模式更糟：两个管理员各自发过同名技能时，
「我发的那份被对方悄悄顶掉」在界面上毫无痕迹，而列表里多一条是**看得见、可以自己删**的。
需要改一份已发布的资产就走 PATCH。

### 2.5 判据

`cloud/tests/test_org_assets.py`（13 例）。三条核心：

- `test_member_cannot_publish` —— 成员发布 → **403**（不是 404：他确实是成员，只是角色不够）。
- `test_reject_machine_specific_keys` —— 顶层 `path` 与**嵌套** `imBinding` 都被 400 拦下，
  且文案点名到具体键。
- `test_cross_org_asset_is_404` —— 同一个人是两个组织的 owner，拿 A 的资产 id 去 B 路径下
  DELETE / PATCH 都 404，且 A 组织里那份仍然在。

其余：成员可见 + 发布者邮箱 / kind 筛选 + 未知 kind 400 / 非成员列表与撤回 404 /
形状校验（缺 prompt、坏槽位）/ 超限 / PATCH 改名与改载荷 / **PATCH 也重新校验**（否则可以
先发一个合法技能再改成空壳）/ 撤回后列表为空 / 成员不能撤回 / 未知 kind 进 422。

## 三、客户端

### 3.1 文件分工

| 文件 | 职责 |
|---|---|
| `src/types/orgAsset.ts` | 类型契约、种类标签、`org:<assetId>` 本地 id 规则 |
| `src/lib/orgAsset/orgAssetPayload.ts` | **纯函数**：上传方向白名单构造 / 落地方向脏数据防御 / 发布候选与草稿 |
| `src/lib/orgAsset/orgAssetClient.ts` | 云端网关（走 `lib/net/authedRequest.ts`，401 换票只有那一份） |
| `src/sync/orgAssetGateway.ts` | 装配（唯一装配处，与 `projectGateway.ts` 同构） |
| `src/pages/orgAssets/OrgAssetsPage.tsx` | 列表 / 发布 / 撤回 / 添加到我的 |

### 3.2 上传方向是**白名单**，不是「删敏感字段」

`agentPayload` / `skillPayload` 逐个字段挑出来。黑名单式的 `{...agent, path: undefined}`
会在下次给 `Agent` 加字段时静默泄露 —— 而那正是最不容易被 review 到的时刻。

三个「必须原样保留」的字段：

1. `toolAllow` / `toolDeny` 的**存在性**：空数组 = 一个工具都不许，省略 = 不限制。
   用 `?? undefined` / `?? []` 归一化会把最严的配置变成最松的（FR-2.2）。
2. 专家的 `model`：导入端只在**本机确实有这个预设**时才保留，否则丢弃并提示 ——
   失效预设名会让引擎每轮报错。
3. 技能的 `prompt` 正文逐字不动。

`data:` 开头的头像**不上云**：一张头像能吃掉 64 KiB 上限的大半，而它只是张图。

### 3.3 落地方向：三种资产三种落地方式（刻意不统一）

| 种类 | 落地动作 | 本地 id | 重复导入 |
|---|---|---|---|
| 专家 | `agentsStore.importAgent(draft)` | 新 uuid | **再来一份**（可编辑的个人副本） |
| 技能 | `skillsStore.installSkill(skill)` | `org:<assetId>` | **覆盖**（按 id） |
| 提示词 | `PromptLibrary.save(kind, key, text)` | 槽位 key | **覆盖**（覆盖前确认） |

这不是不一致，是三种资产的性质不同：技能是「装上 / 卸下」型资产（唯一来源才是对的），
专家是可编辑的个人副本（导入两次得到两份，各自独立改），提示词模板本身就是「每个槽位一份」。

专家重名**复用** `lib/agent/expertPackage.ts::dedupeExpertName`（本次为此把它导出）：
「导入进来的专家重名怎么办」必须只有一个答案，两份实现迟早分叉成
「从包导入叫（导入 2）、从组织资产导入直接撞名」。

### 3.4 权限只认服务端给的角色

页面用 `KbOrg.role`（组织接口已经算好的值）判断「能否发布 / 撤回」，判据与 `ProjectsPage`、
`KnowledgePage` 一致（`role === 'admin' || role === 'owner'`）。**不在前端重算权限**，
也不靠「接口会不会 403」来试探。

### 3.5 导入不重复记账

专家走 `importAgent`（记 `agent.import`）、技能走 `installSkill`（记 `skill.install`），
两条路径本来就有记账点；再补一条 `orgAsset.import` 会让同一个动作在审计里出现两条
（「谁改的」反而更难读）。只有提示词模板那条路径（`PromptLibrary.save`）本来没有记账点，
才由页面补 `orgAsset.import`。

新增的三个动作：`orgAsset.publish` / `orgAsset.withdraw` / `orgAsset.import`
（登记在 `lib/audit/appAudit.ts` 的闭集与「组织资产」分组）。

### 3.6 判据

- `tests/lib/orgAsset/orgAssetPayload.test.ts`（23 例）：白名单不泄露 / `toolAllow: []` 不被抹平 /
  data 头像不上云 / 候选排除内置项 / 未知技能与失效模型被丢弃并给说明 / 预设目录未加载时不校验 /
  脏载荷不炸 / `landSkill` 的 id 与可删性 / `landPrompt` 的三道校验。
- `tests/orgAssetsPage.test.tsx`（13 例）：未登录文案 / 列表与发布者 / 管理员看得到发布·编辑·撤回、
  成员看不到但仍能「添加到我的」/ **添加到我的真的往 store 加了一条** / 撤回要先确认且
  按 `(orgId, assetId)` 调一次 / 取消不发请求 / **发布链路真的把剥干净的载荷送出去** /
  服务端错误文案原样显示 / **编辑弹窗回填现值且只送改过的字段** / **没改就不发请求** /
  编辑失败弹窗不关且显示服务端原话。

## 五、补充：编辑能力（2026-11-03）

### 5.1 开的是什么口子

列表行多了「编辑」（仅 `admin` / `owner`），弹窗改 **名称** 与 **说明**，走 `PATCH`。
面板里明写一句「内容本身是发布时的快照，改内容请撤回后重新发布」，把边界说在用户眼前。

### 5.2 为什么只改元信息，不给改载荷

三条理由，任何一条都足够：

1. **载荷是快照，不是引用**（本模块的前提）。组织侧没有版本链，改了无从回溯改了什么。
2. **会与别人本机那份对不上**。对方导入的是旧内容，组织里显示的是新内容，
   而「谁导入了哪一版」这件事系统根本没记。
3. **改内容 = 一次新的发布**，语义上就该是撤回 + 重发：它会产生一条新资产，
   发布人与时间都是新的，追责链条才完整。

### 5.3 只送改过的字段（这条容易做错）

界面拿的是整表单，但 `PATCH` 只该收**真正变过的项**。整表单回传有两个后果：
说明没动也被写一次 `updated_at`，以及审计里出现一条「改了什么也没改」的空账。
判据钉住了这一点（变异：把 `description` 改成无条件回传 → 2 例红）。

### 5.4 审计

新增 `orgAsset.update`（与 `publish` 分开：不然审计里分不清是新增了一条还是改了一条）。
`detail` 只记**字段名**（`fields: "name"`），不记值——审计要能回答「改了什么」，
但它不是内容仓库。

### 5.5 服务端端到端验证（首次真 HTTP）

此前只有 pytest 的 `TestClient`。2026-11-03 在本机起了一个原生实例（临时库、8911 端口），
用真 HTTP + 真 SQLite 跑了 26 项：注册/建组织/加成员、四类载荷护栏（`path`、`imBinding`、
**递归嵌套的 `path`**、缺字段、未知 kind）、member 发布·改·撤全 403、非成员列表 404、
跨组织 id 404、`toolAllow: []` 原样保留、`PATCH` 改名、`DELETE` 撤回后列表为空。
**26/26 通过**；`docker/verify.py --routes-only` 报「必需路由齐全（4 条）」。

结论：路由挂载、表创建（全新库）、权限判定在真实进程里都对得上，不是只在 TestClient 里成立。
