# 同步裁决的第二级 tie-break：跨钟比较（待决）

> **状态**：**待决**（2026-10-31 立项）。当前实现可用，但有一条门禁因此保持红 —— 明确登记，**不掩盖**。
> **影响面**：`FR-10.3` 双向同步；所有可同步实体（Agent / 专家团 / 任务 / MCP / 渠道 / 技能覆盖 / 会话 meta / 设置）。
> **相关提交**：2026-10-31 的「裁决键改为 `rev` 优先」修正（`cloud/app/sync/merger.py` + `cloud/tests/test_merger.py`）。

## 一、结论

现在的裁决键顺序是 **`rev` → 时间 → id**（2026-10-31 的修正）。`rev` 优先解决了
「单设备连续修改被时钟漂移吃掉」这个真问题。

剩下的问题在**第二级**：`rev` 相等时比时间，而

- 服务端这一侧的时间是**服务端接收时刻**（`row.updated_at`），
- incoming 的时间是**客户端上报值**（`entity.updatedAt`）。

**这是两个不同的钟。** 本机容器比宿主快约 **1.1 秒**，于是「后 push 的那次」的客户端时间
反而**更小** → 同 `rev` 的真并发被判反 → **后改的修改被丢弃**。

## 二、实测（2026-10-31）

- 门禁②「并发改 LWW 收敛」**稳定红**（`expected 'A-edit' to be 'B-edit'`），
  单独跑 4.79 秒同样红 —— 与并发无关。
- 插桩实测（时间戳取自测试进程本机钟）：

  | 时刻 | 值 |
  |---|---|
  | A push 后本地 a1 | `rev=2, updatedAt=11:40:02.964Z` |
  | B push 前本地 a1 | `rev=2, updatedAt=11:40:03.021Z`（确实更晚） |
  | B push 后本地 a1 | `rev=2, name=B-edit`（**B 本地是对的**） |

  → 输在**服务端裁决**，不在客户端。
- **合并语音分支后，原先绿的「门禁①」也开始红，且时序敏感**：
  在测试里加两行 `console.log` 打印冲突快照，它又转绿（`conflicts: []`、`status: synced`）。
  原因是同一根因的另一副面孔：同 `rev` 时跨钟比较会**随机地**判成「服务端更新」→
  记成 conflict；语音分支给 `settings` 加了字段（迁移 v15 + provider），使「同 `rev` 但
  内容不同」的路径第一次被走到，于是这条不稳定路径暴露出来。
  → 门禁①与门禁②是**同一个缺陷的两种表现**，不要当成两个问题分别修。
- **试过最小修法并回退**：把服务端 `current` 的时间改成
  `row.client_updated_at or row.updated_at` → **门禁①反而变红**
  （「B 改 → A 换回拿到 B 改动」这条主链路被打断）。
  原因：客户端 pull 到的 payload 里 `updatedAt` 是**服务端归一后**的值（m6 §5.3），
  服务端改用客户端钟、客户端仍用服务端钟 → 两端不同源，问题从一处搬到另一处。
  代码里留了说明注释（`cloud/app/sync/routes.py` 的 `current` 构造处）。

## 三、三个方案

| 方案 | 做法 | 收益 | 代价 |
|---|---|---|---|
| **A. 同源化** | payload 不再归一（下发客户端上报值）+ 服务端 `current` 用 `client_updated_at` | LWW 回到经典语义（参与者钟大致同步），「谁更晚改」可判定 | **推翻 m6 §5.3 的既定决策**；影响全部实体的 pull 结果；要重新推导「30s 一次无限写入」是否仍被「完全同版幂等跳过」兜住（初步看能兜住） |
| **B. 服务端权威版本** | `rev` 由服务端分配（客户端只提交内容） | 根治，无时钟依赖 | 最大：协议 + 全部实体 + 冲突流程都要重做 |
| **C. 承认冲突** | 同 `rev` 时**先到者胜**，并让客户端**显式提示冲突**（保留双方版本） | 确定、与钟无关；把「静默丢弃」变成「用户知道没同步过去」 | 需要「冲突提示」的产品口径与界面；后改的修改**会被丢弃**（但不再静默） |

## 四、建议

**先 C 后 A**：

- **C 是数据正确性底线** —— 现在「用户刚改的内容被丢掉且没有任何提示」，这比「谁赢」重要；
- **A 解决「谁更晚改」的正确性**，但要先推翻 §5.3，需要一轮完整的文档 + 用例重推
  （§5.3 的推导散在 `architecture-m6-sync.md`、`cross-platform-sync-design.md` 与 PRD §19）。
