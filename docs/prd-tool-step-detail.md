## 0. 项目信息

| 项 | 值 |
|---|---|
| Language | 中文 |
| Programming Language | 沿用现状技术栈（React 18 + TS + Vite + MUI + Tailwind）；**不引入新依赖** |

## 1. 产品目标（3 条，正交）

1. **够用即止**：用户按需选择过程详略——日常只看结论、需要时看关键动作、排障时看全量思考与工具调用。
2. **异常永不隐身**：失败 / 引擎中断等异常信号在**任何档位、任何折叠态**下都必须可见，不因简化而被吃掉。
3. **一次配置、全局生效、最小改动**：档位作为一项全局偏好落进既有设置体系，不新增同步/持久化机制、不重写消息渲染架构。

## 2. 现状与问题

- 过程数据模型 `ProcessEvent = ReasoningEvent | ProcessToolRow`（`src/types/process.ts`），按 SSE 到达顺序 push 到 `Message.process`，**思考段与工具行交错**。
- 渲染 `ProcessView.tsx`：按序铺开 `reasoning→<ReasoningBlock>` / `tool→<ToolRow>`，自身不折叠、不限高，可见性交给调用方。
- 装配 `AssistantMessage.tsx`：签名头 → 过程开关行（`已处理/已完成 + 耗时 + · N 步失败`）→ `<Collapse unmountOnExit>` 包 `ProcessView` → 卡片产物 → 正文 → 状态行 → 富产物 → 文件产物 → 计划卡片。可见性规则：`processOpen = searchForcesOpen || (manualProcessOpen ?? isStreaming)`（**流式中自动铺开、结束后整块收起**）。
- **问题**：详略是「一刀切」——要么全铺开（长任务的思考标记+工具行能顶掉一整屏，把结论推出视口），要么全收起（想看哪步失败又得整块展开）。用户无法表达「只要结果」「只要关键动作」这类中间诉求。

## 3. 三档定义

### 3.1 命名与内部值

| 展示名 | 内部值 | 一句话含义 |
|---|---|---|
| 聚焦结果 | `result` | 只看结论，界面最简。过程中的常规动作全部不渲染。 |
| 关键细节 | `key` | 结果优先，仅保留重要步骤与关键操作；琐碎的读/查聚合为一行。 |
| 完整过程 | `full` | 完整工作过程（思考正文 + 全部工具行），供调试排障。 |

类型：`export type ProcessDetailLevel = 'result' | 'key' | 'full';`

### 3.2 逐元素可见性契约（唯一事实源）

「过程细节」被定义为下列元素；档位**只**过滤其中标 ◐ / ○ 的行，标 ● 的对档位免疫。

| # | 元素 | 聚焦结果 `result` | 关键细节 `key` | 完整过程 `full` |
|---|---|---|---|---|
| A | 深度思考**标记行**（「深度思考」） | ○ 不渲染 | ◐ 渲染（折叠一行） | ◐ 渲染（折叠一行） |
| B | 深度思考**正文** | ○ 不渲染 | ◐ 仅「当前 live 段」流式中展开；已写完段默认折叠、点击展开 | 同 `key`（正文按需展开，不默认全文铺开） |
| C | 工具执行行（done，**关键**工具） | ○ 不渲染 | ● 逐行渲染 | ● 逐行渲染 |
| D | 工具执行行（done，**非关键**工具） | ○ 不渲染 | ◐ 按连续段聚合成 1 行摘要（可展开，见 §4.2） | ● 逐行渲染 |
| E | 工具执行行（**running**） | ● 恒渲染 | ● 恒渲染 | ● 恒渲染 |
| F | 工具执行行（**error**） | ● 恒渲染（红字「失败」） | ● 恒渲染 | ● 恒渲染 |

| I | cron 卡片 / 计划卡片(PlanCard) / 文件产物 / 富产物 / 正文 | ● 恒可见 | ● 恒可见 | ● 恒可见 |

### 3.3 关键裁决

1. **失败信号在「聚焦结果」档仍强制暴露（裁决：是）。**
   - 理由：2026-09-29 断流事故的教训是「异常不能藏在折叠区里」。因此本档不采用「只留一个计数」的弱暴露，而是**双重强制**：
     - (a) 开关行的红色「· N 步失败」聚合信号——**三档恒常驻**、不随折叠消失（沿用现状）；
     - (b) error 工具行是**档位豁免项**（E/F），任何档位都渲染，绝不被过滤；
     - (c) **只要 `errors > 0`，过程块结束后不自动收起**（见 §5.1 状态机），因此聚焦结果档下那条红行默认就是可见的。由于本档过滤后过程块里**只剩** running/error 行，展开它至多几行红字，不会造成洪泛——这正是「安全」与「简洁」可以同时成立的原因。
   - 结论：聚焦结果 = 简洁，但**绝不隐藏异常**。
2. **running 行是「进行态」，不是「历史细节」（裁决：恒渲染）。** 流式期间用户必须知道「此刻在做什么」；它随 status 变化而消失，不构成对「简洁」的长期负担。
3. **卡片类产物不属于「过程」（裁决：恒可见）。** 计划卡片是「本轮唯一需要用户做决定的东西」；审批/敏感卡片需要用户判断与授权；cron 卡片、文件/富产物是**结果**。它们一律移出过程块（其中审批/敏感 ToolCallCard 需从 `ProcessView` 的 `children` 上移到 `Collapse` 之外）。

## 4. 「关键步骤」分类口径

### 4.1 可判定规则（白名单，fail-open）

```
非关键（non-key）= 纯只读、无副作用的本机信息收集：
    read_file · list_dir · find_files · grep
关键（key）= 其余全部，含：
    write_file · edit · edit_file · exec · cron · mcp_*（前缀匹配）
    · web_search · x_search · web_fetch · 以及任何未知/新增工具名
```

- **判定方向是「只读白名单」而非「关键名单」**：未知工具一律按**关键**处理（宁可多做展示，也不静默吞掉一个可能重要的动作）。
- 对用户原话的一处**显式细化**：用户把「搜索」与「读文件/列目录」并列为非关键，本 PRD 将「本机检索（grep/find_files）」归为非关键，而把**联网动作（web_search/web_fetch/x_search）归为关键**——它们是外部动作，有网络成本与不确定性，用户通常关心「模型上网查了什么」。（若产品后续想改，只需调整这一张白名单，见 §12 Q1。）

### 4.2 非关键行在「关键细节」档的呈现（推荐：按连续段聚合为可展开的单行）

- 把**相邻的**非关键行合并成**一条汇总行**，位置保持原顺序（不把所有非关键行抽到一块），从而保留「模型动作轨迹」的可读性。
- 汇总文案：按桶计数，固定顺序 `已读取 N 个文件 · 已浏览 N 个目录 · 已查找 N 次 · 已搜索 N 次`，只列出计数 > 0 的桶，以 ` · ` 连接。
- 汇总行**默认折叠为一行**，**可点击展开**为原始单行（每个过程块内独立维护展开态，不持久化）。
- 取舍：相比「完全隐藏」，聚合+可展开多一层交互，但保住了「顺手看一眼读过哪些文件」的诉求，且避免了「想看个细节要先改全局设置」的坏体验；相比「全部逐行」，它才是「关键细节」档的核心价值。

### 4.3 示例

原始序列：`R1 → read a.ts → read b.ts → grep "foo" → edit c.ts → read d.ts`
- `key` 档渲染：`深度思考`（折叠）→ **[已读取 2 个文件 · 已搜索 1 次]** → `已编辑 c.ts` → **[已读取 1 个文件]**
- `full` 档渲染：`深度思考` → `已读取 a.ts` → `已读取 b.ts` → `已搜索 "foo"` → `已编辑 c.ts` → `已读取 d.ts`

## 5. 状态机与优先级（档位与「流式铺开 / 结束收起」如何共存）

**裁决：档位是「默认展开态**+**渲染契约」，不是「替代」手动控制；手动与搜索仍然最高优先。**

### 5.1 展开态决策

```
defaultProcessOpen(tier, isStreaming, errors) =
    errors > 0        ? true               // 有失败：任何档位都保持展开（安全优先）
  : tier === 'full'   ? true               // 完整过程：不再自动收起（调试者的诉求）
  :                     isStreaming        // result / key：流式中展开，结束后收起

processOpen = searchForcesOpen || (manualProcessOpen ?? defaultProcessOpen(...))
```

- `errors` 取 `digestProcess(filteredEvents).errors`（沿用 `src/lib/processDigest.ts`）。
- `full` 档结束后**保持展开**（这是对本需求「完整过程方便调试」的直接落地，也是本档相对 `key` 的关键差异之一）；用户仍可手动收起。

### 5.2 优先级（高 → 低）

1. **搜索强制展开** `searchForcesOpen`（命中项藏在折叠区会搜不到）—— 最高，任何档位、任何手动状态下都强制展开。
2. **用户手动表态** `manualProcessOpen`（点过开关行之后以其为准）。
3. **档位默认** `defaultProcessOpen(tier, isStreaming, errors)`。

### 5.3 与既有不变量的关系

- 「流式中自动可见」在三档下**全部保留**（`result/key` 靠 `isStreaming`，`full` 恒开）。
- 「结束后收起」仅在 `key` 档保留原样；`result` 档在无失败时才收起；`full` 档不再收起——**这是有意的行为变更**。
- 「搜索强制展开」「手动优先」两条既有不变量的优先级与语义**完全不变**。

### 5.4 chevron / 可点击性

- `tier !== 'result'`：有过程内容即可点击（同现状）。
- `tier === 'result'`：**仅当** `running > 0 || errors > 0` 才渲染 chevron 并可点击（否则「已完成 + 耗时」退化为一行不可点的状态文案）。

## 6. 设置项设计

### 6.1 落点（裁决：放进现有「通用」分区新增一张卡片）

- 理由：① **最小变更**——新增菜单分区需要同步 `settingsNav.tsx` / `settingsUiStore.SETTINGS_SECTION_IDS` / `SettingsDialog.SectionBody` / `tests/settingsDialogSections.test.tsx` 的 `CONTENT_ANCHORS` 四处穷尽性检查，成本与风险都高于收益；② 「通用」已是「这台机器上我怎么用」的偏好归集地（主题 / 桌面端 / 存储），展示详略同属此类；③ 既有锚点 `general: '外观'` 不变，设置测试无需改动。
- **明确不做**：不新增设置分区 id（列 P2，见 §8）。

### 6.2 控件与文案

- 控件：**`ToggleButtonGroup` 三选一**（与「通用 → 外观 → 主题」同一控件语言），值为 `result | key | full`。
- 卡片标题：**对话过程**
- 卡片说明（两行以内）：
  > 控制对话中模型工作步骤的展示详略。聚焦结果只看结论；关键细节仅展示重要操作；完整过程保留全部思考与工具调用。
- 行标签：**工作步骤展示**；行 hint：**出错时始终会标出失败步骤，不受本设置影响。**（把 §3.3 的安全承诺直接讲给用户）

### 6.3 默认值（裁决：`key`「关键细节」）

- 理由：三档中没有一档能逐像素复刻现状，只能选**扰动最小**者。`full` 会改掉「结束后收起」，`result` 会改掉「流式铺开看到动作」的既有主体验；`key` 保留「流式中看到过程、结束后收起」这条主线，同时把琐碎读取收敛为一行——是唯一的中间档，用户可向任一方向移动。
- 代价（显式承认）：老用户在 `key` 档下会发现「读文件/搜索」不再逐行列出，而是折叠成一行汇总——这是本需求**有意**带给全部老用户的观感变化。

### 6.4 生效范围（裁决：全局）

- 全局设置（对齐现有设置体系全部为全局的事实）。理由：过程详略是稳定偏好，不随会话变化；会话级覆盖需新增会话字段 + 持久化 + UI，违背最小变更。
- 会话级覆盖列 **P2**（见 §8），本次不做。

### 6.5 数据契约（实现约束，务必逐条落实）

| 项 | 要求 |
|---|---|
| 字段 | `Settings.processDetail: ProcessDetailLevel`（`src/types/settings.ts`） |
| 默认 | `DEFAULT_SETTINGS.processDetail = 'key'`（`settingsStore.ts`） |
| 归一化 | 新增 `normalizeProcessDetail(value): ProcessDetailLevel`，非法值兜底 `'key'`（对齐 `normalizeTheme` 写法） |
| 版本 | `version: 12 → 13`；`migrate()` 内显式补 `state.settings.processDetail = normalizeProcessDetail(state.settings.processDetail)` 并注明「v13」 |
| 持久化 | `partialize` 已整体输出 `settings`，新字段自动落盘，无需改 `partialize` |
| 同步 | **同步**（纯偏好）。`processDetail` **不得**加入 `SETTINGS_SYNC_OMIT_KEYS` |

## 7. 用户故事与验收标准

**User Stories**
1. 作为日常用户，我默认只看到结论与重要动作，不必被一串读文件行淹没。
2. 作为排障者，我切到「完整过程」后能看到思考正文与全部工具调用，且它不会在结束后自动消失。
3. 作为任何用户，只要某一步失败或本轮被引擎中断，我一定看得见，不会误以为成功。
4. 作为想长期固定的用户，我在设置里改一次就全局生效、重启保持。

**Acceptance Criteria（Given / When / Then）**
- AC1 给定设置 `processDetail='result'`，当消息含 5 条 done 的 read_file 时，则过程块不渲染这些行，开关行显示「已完成 + 耗时」且无 chevron。
- AC2 给定任一档位，当某工具行 `status='error'` 时，则该行在过程块内**始终**存在（不被档位过滤），且开关行显示红色「· N 步失败」。
- AC3 给定 `errors>0`，当流结束（非流式）时，则过程块**保持展开**（三档一致）。
- AC4 给定 `tier='full'`，当流结束（非流式）时，则过程块仍展开；用户点开关行后可收起。
- AC5 给定 `tier='key'`，当消息含连续 3 条 read_file（done）时，则它们聚合为一条汇总行「已读取 3 个文件」；点击该行后展开出 3 条原始单行。
- AC6 给定任一档位、任一折叠态，当 `message.interrupted` 为真时，则中断警告可见。
- AC7 给定搜索命中态（`searchForcesOpen`），当用户处于 `result` 档时，则过程块强制展开，优先级高于手动状态与档位默认。
- AC8 给定任意 `processDetail` 值被手工写成非法串，当读取设置时，则归一化为 `'key'`。
- AC9 给定运行中（`status='running'`）的行，当处于 `result` 档且流式中时，则该行可见。
- AC10 给定 `processDetail='full'`，当设置被云同步时，则 `processDetail` 出现在同步负载中（不被 omit）。

## 11. 约束

1. **增量、最小变更**：不得重写消息流架构（`Message.process` 数据形态、`ProcessView` 的「按序铺开、不自带折叠/限高」职责不变）。
2. **新增 `Settings` 字段必须**：配默认值、`version` 升级 + `migrate()` 补齐、确认 `partialize` 覆盖（现为整体输出，自动覆盖）、确认同步策略（纯偏好 → 同步，**不得**进 `SETTINGS_SYNC_OMIT_KEYS`）。
3. **不新增设置分区 id**（P0 范围内）；若将来新增，必须同步 `settingsNav.tsx`、`settingsUiStore.SETTINGS_SECTION_IDS`、`SettingsDialog.SectionBody`、`tests/settingsDialogSections.test.tsx` 的 `CONTENT_ANCHORS`（穷尽性检查，漏一处编译期报错）。
4. **代码风格**：`src/stores`、`src/lib`、`tests` 用**单引号**；`src/pages`、`src/components` 内已有文件混用双引号——**改哪个文件就跟随该文件现有风格**，不做整体格式化。注释只写「为什么」，不写「做了什么」。
5. ⛔ **禁止任何 git 写操作**；**不得修改 `nanobot/` 目录**。
6. 新增依赖：**零**。

## 12. 待确认问题

- **Q1（分类口径微调）**：`web_search / web_fetch / x_search` 本 PRD 归为「关键」。若产品希望严格照用户原话把「搜索」并入非关键，仅需改动 §4.1 白名单一行，其余契约不变。
- **Q2（消息内快捷切换，P2）**：本 PRD **倾向不做**消息内档位切换——档位是全局单一事实源，消息级覆盖会让「这条消息为什么和别的不一样」难以解释；消息级已有「展开/收起」这一本地控制。若要做，建议语义为「跳转到设置分区」而非就地改档。请确认是否维持「不做」。
- **Q3（`result` 档失败行呈现）**：本 PRD 选择「error 行恒渲染 + errors>0 时不自动收起」，即以一条红行换取 100% 的异常可见性。若产品更偏好极致的「只看结果」，可降级为「仅保留红色计数、失败明细需切档」——但会与 2026-09-29 教训的立场相冲突，**不建议**。
